# V1 Baseline Sync Checklist

> 目标：把需求、技术设计、原型、ADR 同步到同一套 V1 基线，并让 Capability Manifest 能追溯。
>
> 本文不是 spec，不定义 DTO、表字段或实现细节。

## 1. 真源优先级

1. ADR 0010–0023：最新裁决。
2. `docs/requirements/v1-requirements.md`：产品行为。
3. `docs/technical/nestjs-backend-design.md`：服务、数据、API、非功能约束。
4. `prototype/`：UI 验收基线。
5. `docs/planning/v1-capability-manifest.md`：覆盖检查表。

冲突处理：先改基线，再 `/to-spec`；不允许在实现阶段自行选一个。

## 6. Capability Manifest 覆盖

- [ ] 每个 V1 能力有至少一个 ticket 归属。
- [ ] 每个 ticket 至少引用一个 V1 能力。
- [ ] 每个能力有原型页面/动作或“无 UI（后台能力）”标记。
- [ ] 每个能力有 API/Worker、数据约束、验收证据。
- [ ] 没有孤儿 ticket，没有无 ticket 能力。
- [ ] `后续` 能力不进入 V1 发布门禁。
- [ ] `原型专用` 控件不进入生产 UI。

## 7. Baseline Synced 的定义

以下全部满足，才算基线同步完成：

- 需求、技术、原型、ADR 不再互相矛盾。
- Capability Manifest 的 V1 能力全部有归属和验收证据。
- 原型按 ADR 0012 修正并重新签收。
- 页面/动作/API/状态矩阵、组件清单、设计令牌、Playwright 基线存在。
- 10M 规模、成本、索引、备份和压测目标已重算。
- 安全与数据生命周期契约已进入技术设计。
- 质量 rubric、基准集、回归门禁已定义。
- 没有“先用假接口/假数据”才能继续的 P0 缺口。

## 8. 执行顺序

1. 先确认 Capability Manifest v1 的域和 ID 没有遗漏。
2. 同步需求文档。
3. 同步技术设计。
4. 修正并签收原型。
5. 补页面/动作/API/状态矩阵。
6. 做第五轮评估；通过后才 `/to-spec`。

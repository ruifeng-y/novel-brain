## 2. Recovery Evidence

`apps/api/test/manuscript-import-chunked.integration.test.ts` exercises the public HTTP
lifecycle:

- streamed start and sequential chunk append;
- bounded requests below 1 MB per chunk;
- legacy batch endpoint capped at 500,000 characters and rejects larger payloads with `400`;
- mismatched replay of an existing chunk sequence rejected instead of silently ignored;
- partial upload failure and retry;
- idempotent pause/resume and process suppression while paused;
- real `process_import` Worker jobs with explicit null work scope and a durable checkpoint;
- a real BullMQ queue/worker with the production 10-chunk tick, Redis delivery loss and two
  PostgreSQL-backed recovery deliveries for a 12-chunk import;
- Playwright starts and kills a real BullMQ Worker process;
- app restart while processing, followed by continued processing from the last committed
  sequence and parse checkpoint;
- forced Worker failure, followed by pause/resume and a new Worker processing the failed
  chunk from its pending state;
- `SIGKILL` while a real Worker owns an active import job, BullMQ stalled-job recovery and a
  replacement Worker continuing from `nextProcessSequence`;
- periodic PostgreSQL-backed recovery scanning for queued/processing imports with pending
  chunks under a dedicated RLS-scoped `import_recovery` system policy, so Redis delivery loss
  does not strand durable import state;
- cancel and rejection of append after cancellation;
- repeated cancel, rejected confirmation after cancellation and cross-tenant denial;
- rejection of malformed UTF-16 before a chunk can enter durable source storage;
- range-only confirmation without sending 10M characters in one request;
- confirmation response below 200 KB, containing work metadata instead of chapter text;
- replay confirmation without duplicate chapters or versions;
- `canConfirm` remains false during queued, processing, paused and partial states;
- source ranges covering exactly `0..10,000,000`;
- rejection of a range that splits a surrogate pair.

The Worker advances only the exact chunk selected by `nextProcessSequence`. A failed chunk
sets the import to `partial` and blocks later chunks until `resume` resets the failed chunk;
this prevents later chunks from advancing the global parser offset out of order.

Recorded local run:

| Metric | Value |
| --- | ---: |
| Elapsed | `14,936 ms` |
| Peak process RSS | `599,445,504 bytes` |
| Chunk request ceiling asserted | `< 1,000,000 bytes` |
| Processed chunks | `40 / 40` |
| Imported chapters | `4,000` |

The memory bound is for this fixture and environment, not a universal throughput or
capacity claim. The test fails if peak process RSS reaches 768 MiB. The parser keeps at
most one source chunk plus bounded checkpoint metadata; preview does not materialize the
full source, boundary checks load one chunk at a time to apply JavaScript UTF-16 offsets
exactly, and confirmation reads source ranges into a streaming chunk cursor in batches.

## 3. Production UI Evidence

`apps/web/e2e/parity/new-project.spec.ts` covers the production `new-project` flow:

- one injected chunk-upload failure followed by real API retry;
- received/processed chunk progress;
- pause while a real Worker is processing;
- a real Worker process crash while processing, replacement Worker and BullMQ stalled-job
  recovery;
- a real Worker chunk failure, visible partial state, Worker restart and resume;
- metadata-only preview with server-retained source;
- confirmation rejects any single chapter over 200,000 characters, preventing a range from
  materializing the whole manuscript in application memory;
- range-based confirmation through the real API;
- four viewports: 390, 900, 1180 and 1440;
- full-page attachments for upload failure, paused, partial failure and preview states at
  all four viewports;
- no horizontal overflow.

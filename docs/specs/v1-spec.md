# NovelBrain V1 Spec：单作者长篇 AI 创作平台

## Problem Statement

非专业个人作者有故事想法，但缺少长篇写作的结构能力、持续产能和一致性维护能力。现有 AI 写作工具能生成段落，却无法在百万字尺度上维持人物、势力、地图、战力、时间线和伏笔的一致性；也无法区分客观真相与角色认知，无法安全地修改已写内容，无法在改坏之后回滚。作者最终得到的是一堆互相矛盾的章节，而不是一本可以连载的书。

## Solution

NovelBrain 是一个面向个人作者的 Web 创作平台。作者从一个想法或部分设定出发，生成故事圣经、题材化设定、大纲、章节和正文。平台以正史作为唯一事实源，正史包含世界事实、角色认知、叙事计划和文本四层。生成时编译当前场景相关的上下文子集，生成后用全量正史校验，确认事实后才提交正史。作者可以按章、按卷、按自定义区间或按全本生成，可以审阅和修改正文，可以拉平行版本做实验，可以回滚而不丢失历史。

V1 是单作者、账号制、BYOK、局域网优先的版本。首批模型供应商是 DeepSeek 官方 API。V1 不做团队、管理员后台、配额、计费、本地模型和直连发布。V1 的完整范围由需求基线定义，M0 到 M3 是交付里程碑，不是四个产品版本。

## User Stories

### 账号与访问

1. 作为个人作者，我想用邮箱和验证码注册，这样我不需要额外完成一次邮箱验证链接。
2. 作为作者，我想用邮箱和密码登录，这样我能安全访问自己的作品。
3. 作为作者，我想通过邮件找回密码，这样我忘记密码时还能恢复访问。
4. 作为作者，我想退出所有设备，这样账号泄露时我能立即止损。
5. 作为作者，我想拥有多个笔名，这样我可以用不同身份写不同作品。
6. 作为作者，我想导出全部作品和设定，这样我能带走自己的数据。
7. 作为作者，我想注销账号并保留 30 天恢复期，这样误操作不会立刻造成永久损失。
8. 作为作者，我想配置自己的 DeepSeek API Key，这样模型用量和费用由我自己控制。
9. 作为作者，我想测试模型连接，这样我知道生成前配置是否可用。
10. 作为作者，我想看到 token 用量和预估费用，这样我能监控消耗，但不需要配额系统。
11. 作为作者，我想为规划、正文和校验分别选择模型，这样不同任务可以用最合适的模型。
12. 作为作者，我想让 API Key 加密存储、界面掩码、日志脱敏，这样我的密钥不会被泄露。

### 作品与分支

13. 作为作者，我想用一句话想法创建作品，这样我能快速开始。
14. 作为作者，我想创建空白作品，这样我能按自己的结构搭建。
15. 作为作者，我想从题材模板开始，这样我能直接获得正确的字段和规则。
16. 作为作者，我想导入 TXT、Markdown 或 DOCX 旧稿并按章节切分，这样我能继续写已有作品。
17. 作为作者，我想看到所有作品的进度、字数、状态和最近编辑时间，这样我能决定先写哪本。
18. 作为作者，我想按状态、题材和最近编辑筛选作品，这样我能管理多部作品。
19. 作为作者，我想归档和恢复作品，这样我的活跃列表能保持干净。
20. 作为作者，我想软删除作品并在 30 天内恢复，这样误删不会造成永久损失。
21. 作为作者，我想复制作品的故事圣经、设定和大纲但不复制正文，这样我能在同一世界观下开新书。
22. 作为作者，我想有一条主线和多个平行版本，这样我能做实验而不污染主线。
23. 作为作者，我想比较平行版本，这样我能决定保留哪一版。
24. 作为作者，我想从平行版本选择性摘取章节、设定或大纲节点，这样我能复用好的部分而不整体合并。
25. 作为作者，我想让已完本作品默认只读，这样已发布内容不会被悄悄修改。

### 故事圣经

26. 作为作者，我想有一页纸故事圣经，包含一句话故事、核心卖点、主角、金手指、世界铁律、主线、结局方向和读者承诺，这样我能一眼看懂这本书。
27. 作为作者，我想让故事圣经链接到详细设定，这样我既能看全局，也能下钻细节。
28. 作为作者，我想锁定故事圣经，这样后续生成会把它当成稳定正史。
29. 作为作者，我想让锁定故事圣经的修改走修改请求和影响分析，这样我不会破坏已写章节。
30. 作为作者，我想在故事圣经里看到连续性提醒、未回收伏笔和最近修改，这样我写作时能看到风险。

### 设定中心

31. 作为作者，我想有固定的顶层设定栏目：世界、势力、人物、地图、力量体系、物品功法、时间线，这样我在不同题材下都能快速找到东西。
32. 作为作者，我想在栏目内使用题材化子类型，这样仙侠、历史、都市有各自的字段，但顶层导航不混乱。
33. 作为作者，我想让每个设定条目包含名称、别名、类型、摘要、描述、标签、作用域、状态、来源、关系、自定义字段和版本历史，这样设定是可追踪的结构化数据。
34. 作为作者，我想自定义文本、长文本、数字、日期、单选、多选、布尔和关系引用字段，这样项目能贴合自己的题材。
35. 作为作者，我想用类型化关系表达隶属、位于、控制、拥有、知道、相信、亲属、敌对和师承，这样世界是一张图，而不是一堆笔记。
36. 作为作者，我想有分层地图、地点节点、连接、旅行时间、势力控制区和带标记点的地图图片，这样仙侠可以有多层界面，历史和都市可以只有一张地图。
37. 作为作者，我想让势力通过时间有效的控制关系挂到地点上，这样领地变化能被追踪。
38. 作为作者，我想让人物档案包含欲望、恐惧、秘密、关系、声纹、弧光、所在地、持有物、伪装、身体状态、知识状态和力量状态，这样人物不会崩。
39. 作为作者，我想区分客观真相和角色认知，这样主角可以相信父母自杀，而正史记录的是仇杀。
40. 作为作者，我想用层级、路径、突破条件、代价、瓶颈、克制和资源来描述力量体系，这样不同题材的成长逻辑都能成立。
41. 作为作者，我想让金手指定义规则、代价、限制和成长曲线，这样它是有约束的能力，不是万能外挂。
42. 作为作者，我想让物品功法记录品阶、效果、代价、归属和限制，这样它们不会被随意使用。
43. 作为作者，我想用纪元、绝对日期、相对时间、持续时长和事件节点描述故事时间，这样时间线可以校验。
44. 作为作者，我想用结构化条目加自然语言约束表达世界规则，这样系统能把它们用于上下文和校验。
45. 作为作者，我想做设定体检，检查必填字段、重名、断链关系、地图势力冲突、时间线缺口和力量体系缺口，这样我能提前修复问题。
46. 作为作者，我想让 AI 整套生成、单个生成、补全缺失字段或按想法改写设定，但输出始终是提案，这样我保留最终决定权。
47. 作为作者，我想在设定、大纲和正文中全局搜索，这样我能快速找到引用。
48. 作为作者，我想看到哪些章节和大纲节点引用了某个设定，这样我改设定前能理解影响范围。

### 大纲与剧情

49. 作为作者，我想用全书、卷、幕、章、场景五层结构规划故事，这样我能在不同粒度上工作。
50. 作为作者，我想在全书总纲里写主题、核心冲突、结局方向、主线、支线、人物弧、分卷节奏、力量成长、地图势力推进和伏笔总表，这样全书有骨架。
51. 作为作者，我想在卷纲里写目标、冲突、反派、地图区域、新人物、力量层级、关键事件、卷末高潮、卷首钩子和伏笔埋设回收，这样每卷有完整弧线。
52. 作为作者，我想在章纲里写章目标、POV、场景、冲突、爽点、信息释放、章末钩子、字数目标、出场人物、地点、时间和必须埋设或回收的伏笔，这样每章有明确任务。
53. 作为作者，我想用场景卡写场景目标、POV、地点、时间、参与者、冲突、转折、信息释放和过渡，这样复杂场景可以提前设计。
54. 作为作者，我想有剧情线账本，管理主线、支线、人物线、势力线、世界线、悬疑线和感情线，这样没有线会被忘掉。
55. 作为作者，我想有伏笔账本，记录埋设章、计划回收章、状态、重要程度、关联实体和读者承诺，这样伏笔不会只埋不收。
56. 作为作者，我想有人物弧光账本，记录起点、欲望、恐惧、谎言、真相、转折和终点，这样人物成长有规划。
57. 作为作者，我想做章级和卷级节奏检查，发现连续动作、连续日常、重复桥段、长期不兑现和钩子密度过低，这样故事不会塌。
58. 作为作者，我想有黄金三章的开篇策略，明确第一钩子、主角出场、世界规则展示、第一个爽点和三章章末钩子，这样开篇能留人。
59. 作为作者，我想拖拽、排序、局部重生成、锁定和解锁大纲节点，这样我能改计划而不重写全书。
60. 作为作者，我想让大纲修改遵守已写区、进行区和未写区规则，这样我不会误改已锁章节。
61. 作为作者，我想在生成前看到准备度检查，知道大纲、设定、正史和模型 Key 是否就绪，这样不会白跑任务。
62. 作为作者，我想有剧情体检，检查未收束剧情线、过期伏笔、剧情漏洞、动机断点、反派降智、战力膨胀、重复桥段、地图时间矛盾、信息越界和节奏塌陷，这样我能修结构问题。
63. 作为作者，我想把大纲导出为 Markdown 或 JSON，这样我能在外部审阅或备份。

### 写作台

64. 作为作者，我想有一个三栏写作台，左侧章节、中间正文、右侧上下文，这样我能在同一屏写作和查设定。
65. 作为作者，我想从章纲生成整章，这样我能快速从计划进入草稿。
66. 作为作者，我想从光标续写、选中重写、扩写、缩写、改视角、加章末钩子、生成三个钩子版本、生成标题和摘要，这样我能精细控制正文。
67. 作为作者，我想选择质量档位、模型配置、字数目标、POV、必须包含、必须避免、参考章节、禁忌词和风格滑杆，这样生成结果符合我的意图。
68. 作为作者，我想看到行内批注，标出连续性、人物声纹、节奏、重复、套路化和逻辑问题，并在右侧看到章级建议，这样我能直接改稿。
69. 作为作者，我想接受修改、忽略并记录原因、让 AI 重写或要求解释，这样我始终掌握修改权。
70. 作为作者，我想有自动保存、本地恢复、版本历史、差异和恢复，这样我不会丢稿。
71. 作为作者，我想让章节有已规划、写作中、待审、已锁定和已发布状态，这样流程清晰。
72. 作为作者，我想小修原地改、中修看影响报告、大修走修订或平行版本，这样我不能悄悄破坏已写内容。
73. 作为作者，我想在章节完成后抽取事件、身体状态、角色认知、位置、力量、物品、关系、剧情线和时间线变化，并让我确认，这样正史保持准确。
74. 作为作者，我想让确认后的事实进入正史并更新摘要和索引，这样下一章生成能用上。
75. 作为作者，我想在生成后自动做连续性和质量检查，这样问题在发布前暴露。
76. 作为作者，我想看到钩子、节奏、信息密度、人物声纹、文笔和连续性六项章级质量报告，这样我知道先改哪里。
77. 作为作者，我想把批量任务中的某一章送回写作台人工处理，这样我能在关键章节精修。

### 批量生产

78. 作为作者，我想创建章节生成、重写修订、事实回填、连续性审计、卷级审计和全书审计任务，这样长任务可以后台跑。
79. 作为作者，我想按章、按卷、按自定义区间或按全本生成，这样我能选择范围。
80. 作为作者，我想让自定义区间必须连续，并在缺前序章节时收到提示，这样正史不会断。
81. 作为作者，我想选择逐章审批、逐卷审批或自动通过，并让高风险事件始终需要确认，这样我能平衡速度和控制。
82. 作为作者，我想看到从准备度到摘要的完整任务流水线，这样我知道任务卡在哪一步。
83. 作为作者，我想让草稿并行、正史提交串行，这样吞吐提高但状态不坏。
84. 作为作者，我想暂停、恢复、取消和从失败步骤重试，这样长任务可控。
85. 作为作者，我想有章节数、输出 token、修订次数、重试次数和软费用提醒等安全上限，这样任务不会跑飞。
86. 作为作者，我想在 Key 失效、余额不足、连续失败、连续性错误率过高或高风险正史冲突时自动停止，这样我不浪费钱也不污染正史。
87. 作为作者，我想有审核队列，低风险章节可批量批准，高风险章节逐章确认，这样我能快而不失控。
88. 作为作者，我想在任务结束后看到完成和失败章节、token 和费用、连续性问题、质量摘要、未回收伏笔和下一步建议，这样我知道发生了什么。
89. 作为作者，我想让全本生成成为父任务加卷子任务，并在卷边界暂停，这样三百万字也能管理。
90. 作为作者，我想在任务完成、需要审核或失败时收到站内通知，这样我不用盯着屏幕。

### 修改与版本

91. 作为作者，我想让设定、大纲、正文、正史事实、分支和作品级修改都走修改请求，这样没有东西能直接写锁定状态。
92. 作为作者，我想直接编辑或让 AI 修改，并在应用前看到差异，这样我能审阅提案。
93. 作为作者，我想看到影响分析，列出受影响的实体、事实、章节、大纲、剧情线、角色认知、地图、势力、战力物品和时间线，这样我知道爆炸半径。
94. 作为作者，我想把影响分为安全、可修复和结构性冲突，并看到建议和置信度，这样我能选对处理方式。
95. 作为作者，我想有一致性检查，覆盖结构、硬规则、事实差异、知识和视角、叙事和下游影响，这样修改能被一致地验证。
96. 作为作者，我想应用安全修改、带修复应用可修复修改、为结构性冲突拉平行版本或取消，这样我有清晰选项。
97. 作为作者，我想忽略误报并记录原因，这样检查器不会挡住合理创作。
98. 作为作者，我想让已写区、进行区和未写区有不同的修改规则，这样我知道什么能改。
99. 作为作者，我想从任意版本点拉 copy-on-write 平行版本，并给它名称、原因、父版本、分叉点和状态，这样实验成本很低。
100. 作为作者，我想并排比较设定、大纲和正文，这样我能决定保留什么。
101. 作为作者，我想 V1 不做自动合并，只做带影响分析的选择性摘取，这样我不会丢细节。
102. 作为作者，我想每次修改都产生新版本，历史不可删除，版本是图，章节、卷和正史都有快照，支持撤销和回滚，这样我永远能恢复。
103. 作为作者，我想有审计记录，包含谁、何时、改了什么、为什么、影响、校验和决策，并可导出，这样我能追溯。
104. 作为作者，我想让 AI 辅助修改只生成提案，不直接应用，这样我始终是最终决策者。

### 导出与发布

105. 作为作者，我想导出 TXT、Markdown、DOCX 和 EPUB，PDF 后续再加，这样我能发布或备份。
106. 作为作者，我想导出当前章、选中章节、自定义区间、整卷、全本或指定平行版本，这样我能选择范围。
107. 作为作者，我想选择是否附带故事圣经、设定附录、大纲、伏笔账本和修改记录，这样我能控制导出包。
108. 作为作者，我想有通用网文、起点和番茄三种格式预设，并配置章节标题、卷标题、段间距、缩进和 UTF-8 编码，这样输出能贴合平台。
109. 作为作者，我想在导出前预览前几章和目录，这样我能发现格式问题。
110. 作为作者，我想让大导出在后台运行，显示进度并保留下载历史，这样我能离开页面。
111. 作为作者，我想让导出文件 7 天后过期并可重新导出，这样存储不会无限增长。
112. 作为作者，我想获得书名、简介、标签和章节名建议，以及读者预览和发布检查，这样我能准备发布。
113. 作为作者，我想让发布检查覆盖书名、简介、标签、题材、封面、前三章钩子、章节字数、敏感内容、AI 内容标识、版权和格式，这样我不会漏平台要求。
114. 作为作者，我想 V1 只导出，不绑定也不自动上传起点或番茄，这样我保持控制。

### 安全、隐私与运维

115. 作为作者，我想密码用 Argon2id 哈希、会话用 httpOnly Cookie、支持退出所有设备，并对登录、验证码、导出和生成限流，这样账号更安全。
116. 作为作者，我想 API Key 用信封加密、界面掩码、永不回传明文、永不进日志、运维不可见，这样模型凭证安全。
117. 作为作者，我想用户数据隔离、数据库行级安全、对象存储前缀、签名链接、TLS、静态加密、每日备份、30 天保留和恢复演练，这样作品可靠。
118. 作为作者，我想日志不记录正文和 Key，保留 30 天，并审计登录、Key 变更、导出和删除，这样隐私和可追溯兼得。
119. 作为作者，我想被告知正文会发送给我选择的模型供应商，平台不用我的作品训练，这样我能做知情选择。
120. 作为作者，我想有隐私政策、用户协议、AI 内容标识说明和 30 天注销窗口，这样我理解自己的权利和义务。

### 里程碑

121. 作为产品团队，我想让 M0 交付从注册到确认一章的 walking skeleton，这样架构能端到端跑通。
122. 作为产品团队，我想让 M1 交付完整仙侠创作闭环，这样一本仙侠书可以连载。
123. 作为产品团队，我想让 M2 加入历史和都市题材包、批量生产、任务中心、修改影响分析和平行版本，这样平台覆盖三题材范围。
124. 作为产品团队，我想让 M3 加入导出、发布检查、数据安全、性能、合规和 V1 验收，这样 V1 可以正式发布。

## Implementation Decisions

### 架构

- 采用模块化单体加独立 Worker，不做微服务、Kafka 或 Neo4j。
- Next.js 负责 UI 和 BFF，NestJS 负责产品 API、认证和领域接口，NestJS standalone Worker 负责长任务。
- 一个 Postgres 作为唯一事实源，Redis 负责 BullMQ、缓存和限流，MinIO 负责本地对象存储。
- Caddy 做同域反向代理，`/api` 转到 NestJS，浏览器和 API 同域，避免 CORS 和跨站 Cookie 问题。
- V1 先局域网 Docker Compose，云上部署后续再做。

### 技术栈

- 前端：Next.js 15、React 19、TypeScript、Tailwind、shadcn/ui、Tiptap、React Flow、TanStack Query、Zustand、Zod。
- 后端：NestJS、Drizzle、Postgres 16、pgvector、Redis、BullMQ、S3 或 MinIO。
- AI：Vercel AI SDK、DeepSeek 官方 API、Langfuse TS SDK。
- 测试：Vitest、Playwright、Testcontainers。
- 认证：NestJS 统一管理 opaque session，Postgres 存 token hash，httpOnly Cookie，Argon2id 密码。

### 领域模型

- 以正史为唯一事实源，正文是正史的渲染结果。遵循 ADR-0001。
- 四层状态：世界事实、角色认知、叙事计划、文本。
- 所有故事数据按作品和分支隔离。主分支从第一天存在，第一切片默认使用主分支。
- 题材包采用核心本体加插件式 pack。M0 只实现仙侠 pack，历史和都市在 M2 加入；历史方向是架空古代或穿越争霸，不做严格真实历史。
- 故事圣经是一页纸宪法加总索引；设定中心是详细结构化数据；两者不是同一个东西。
- 事实必须记录模态：世界事实、角色认知、叙事计划、传闻。角色认知必须带持有人和有效期。
- 剧情线、伏笔和人物弧是独立账本，不是普通备注。
- 已写区、进行区、未写区适用不同修改规则。
- 修改请求是所有锁定内容的唯一写入口。
- 平行版本采用 copy-on-write，版本历史不可删除，V1 不做自动合并。

### 数据模型

- 身份：用户、会话、邮箱验证码、笔名、审计日志。
- 作品：作品、分支、分支提交、附件。
- 正史：实体、实体版本、关系、事实、认知状态、事件、剧情线、伏笔、人物弧、正史提交、正史快照、正史事件。
- 规划：大纲、大纲版本、章节、章节版本、场景、章节摘要。
- 生成：生成请求、上下文包、草稿、批注、连续性问题、质量报告。
- 修改：修改请求、影响报告、校验记录、分支合并。
- 任务：任务、任务步骤、检查点、任务事件、用量记录。
- 模型：模型配置、Prompt 版本、模型调用记录。
- 导出与搜索：导出任务、导出模板、搜索文档。
- 弹性字段用 JSONB，查询关键字段用独立列；章节版本存正文和内容哈希；正史用事件溯源加快照。
- 中文检索 V1 用 pg_trgm、simple tsvector 和 pgvector，不安装 zhparser。

### API

- REST，前缀 `/api/v1`，NestJS Swagger 生成 OpenAPI。
- DTO 用 Zod 和 nestjs-zod，前端类型从 OpenAPI 生成。
- 列表使用游标分页，错误统一返回 code、message、details、requestId。
- 创建类接口支持 Idempotency-Key，修改类接口支持 If-Match 或 version 乐观并发。
- 生成流和任务进度使用 SSE。
- 路由按认证、用户、作品、分支、正史、规划、生成、审校、修改、任务、模型、导出、搜索和健康检查分组。

### 任务与 Worker

- 任务状态：queued、preparing、running、waiting_review、completed、failed、canceled、paused。
- 任务步骤：readiness、brief、context、draft、self_check、revise、extract_facts、verify、review、commit、summarize。
- BullMQ 负责投递、延迟、重试和并发；Postgres 负责任务状态、步骤状态、检查点和业务幂等。
- 草稿可并行，正史提交必须串行；每个分支用 advisory lock 保证同一时间只有一个正史写入者。
- 暂停和取消在当前步骤结束后生效；恢复从最后一个成功检查点继续；重试从失败步骤开始。
- 正史提交失败必须停止后续提交。
- 安全上限：单任务最大章节数、单章最大输出 token、单章最大修订次数、最大重试次数、软性费用提醒。

### AI 与校验

- `AiGateway` 是模型调用接口，生产实现走 DeepSeek，测试用 fake gateway。
- 默认正文模型为 `deepseek-chat`，规划和校验可用 `deepseek-reasoner`，模型名以官方当前文档为准。
- DeepSeek Base URL 为 `https://api.deepseek.com`，OpenAI 兼容。
- 每个用户自带 Key，平台不代付、不兜底、不切换到平台 Key。
- 上下文编译器在核心包中，按 token 预算组装硬约束、相关实体、有效事实、角色认知、未回收伏笔、近章摘要、风格样本和场景计划。
- 关键事实永远保留；预算不足时先减少可选上下文，再拆场景，不静默丢关键事实。
- 校验器把正文拆成事实主张，逐条对全量正史检查冲突、知识越界和规则违反。
- Prompt 版本化，结构化输出用 JSON Schema 和 Zod，模型调用记录 token、费用、延迟和状态。

### 修改与版本

- 修改请求包含标题、原因、目标、旧值、新值、差异、来源、风险、状态。
- 改已确认事实、锁定大纲和作品级设置必须填原因；纯文字润色可不填。
- 影响分析结果分安全、可修复、结构性冲突，并给出受影响章节、建议和置信度。
- 一致性检查六步：结构、硬规则、事实差异、知识和视角、叙事、下游影响。
- 小修原地改并留版本；中修给影响报告并重新校验；大修拉平行版本或明确修订。
- 已发布章节和已锁定正史不能原地覆盖。
- 每次修改产生新版本，版本是图，支持撤销、回滚和导出审计；回滚也产生新版本。
- V1 只有作者本人确认，没有角色审批、评论和管理员。

### 前端

- 现有原型是设计参考，不是生产代码。生产 UI 用 Next.js、React、Tailwind、shadcn/ui、Tiptap 和 React Flow 重写。
- M0 页面：注册登录、作品列表和新建、故事圣经简版、章纲简版、写作台、模型设置、事实确认。
- M0 导航：工作台、作品、故事圣经、大纲、写作台、设置。
- M0 不实现完整设定中心、地图、批量、修改版本和导出，这些在 M1 到 M3 加入。
- 前台不出现“正史”“Canon”“ContextPack”“Agent”等内部词；使用故事圣经、设定集、人物档案、时间线、伏笔清单、已确认设定、平行版本、修改记录、影响范围。
- M0 必须有空状态、加载状态、错误状态、模型连接失败提示和事实确认面板。
- 原型对齐在 M0 spec 之后做，不追求提前把所有未来页面高保真。

### 部署、安全与验收

- 局域网 Docker Compose：Caddy、web、api、worker、Postgres、Redis、MinIO。
- 本地开发用 Mailpit 收验证码和找回密码邮件，生产配 SMTP。
- Postgres 每日备份，保留 30 天，RPO 24 小时，RTO 4 小时，定期恢复演练。
- 日志用 pino，追踪用 OpenTelemetry，错误用 Sentry，LLM 追踪用 Langfuse，指标用 Prometheus 和 Grafana。
- 密码 Argon2id，会话 opaque token，模型 Key 信封加密，限流，审计，日志脱敏。
- 验收标准以需求基线第 12 节为准；V1 完成等于所有 V1 ticket 完成、所有 ticket 验收通过、所有里程碑 gate 通过。

## Testing Decisions

- 好测试只验证外部行为，不验证内部实现细节。
- 主 seam 是 HTTP API 加 Worker 任务契约。产品行为通过 `/api/v1/*`、任务状态、步骤状态、SSE 事件和持久化结果验证。
- AI 调用通过 `AiGateway` fake 实现，返回固定文本和结构化输出，不调用真实 DeepSeek。
- 纯逻辑模块用单元测试：上下文编译器、校验器、正史服务、修改影响分析、token 预算。
- 集成测试覆盖 NestJS 模块、Drizzle 仓储、Postgres 和 Redis，使用 Testcontainers。
- API 测试使用 Supertest 加 Vitest，覆盖认证、作品、分支、生成、修改和任务。
- E2E 使用 Playwright，只跑 M0 happy path：注册、建作品、配 Key、最小故事圣经和章纲、生成一章、事实确认。
- 测试数据使用仙侠样例，包含左臂骨折和父母之死两条连续性场景。
- 现有仓库没有测试先例，本 spec 建立第一套测试模式；后续 ticket 复用同一 seam，不新增产品 seam。
- 验收测试引用需求基线第 12 节的功能、质量、非功能、发布门槛和 Definition of Done。

## Out of Scope

- 团队、成员、邀请、角色矩阵。
- 管理员后台、产品内 admin 角色。
- 配额、计费、充值、在线支付。
- 本地模型、Ollama、vLLM、模型微调或训练。
- 直连起点或番茄发布，平台账号绑定，自动上传。
- 分享链接、公开作品、读者社区。
- 移动端原生 App。
- 定时日更、邮件通知。
- PDF 导出、AI 封面。
- 严格真实历史、史料库和完整时代错置数据库。
- 读者模拟器、作品市场、题材模板市场。
- 历史和都市题材包的完整实现；它们在 M2。
- M0 中的完整设定中心、地图、批量生产、修改版本和导出。
- 自动分支合并；V1 只做选择性摘取。
- 用起点正文或未授权语料训练模型。
- 多语言 UI；V1 中文优先。

## Further Notes

- V1 是需求基线的全量范围，M0 到 M3 是交付里程碑，不是四个产品版本，也不是四份 spec。
- 一份 V1 spec，`to-tickets` 拆成垂直切片 ticket，并给每张 ticket 写验收标准和阻塞边。
- M0 是 walking skeleton，不是发布版；M1 内部 beta；M2 扩大 beta；M3 才是 V1 正式发布。
- 第一张 ticket 必须落地稳定契约：作品和分支、章节版本、正史提交、题材包接口、上下文编译器接口、生成网关、任务步骤和检查点、模型配置。
- 现有原型保留为设计参考；M0 spec 后做一次 M0 对齐，生产 UI 用 Next.js 技术栈重写。
- DeepSeek 官方 API 是首批模型；模型名以官方当前文档为准；每个用户自带 Key。
- 局域网优先，MinIO 本地对象存储，Mailpit 本地邮件，SMTP 生产邮件；云厂商后续再定。
- 需求基线、领域词汇、ADR 和技术设计是本次 spec 的上游文档；后续 ticket 必须使用同一套词汇和契约。
